# Validation

`quran-detect` 0.1 ports the matching algorithm of the Python reference implementation, `quran-matcher` 0.2, and replaces its corpus with verbatim Tanzil text. Two checks support that: a differential parity test against the reference running on the same corpus, and a benchmark gate against the reference's own results.

## Unit and behavioral tests

`cargo test --workspace` runs without network access or Python:

- Every code point assigned in Unicode 15.1 is checked against CPython 3.13 for NFC, NFKC, canonical combining class and pairwise composition, and every HTML5 entity shape the tokenizer accepts is checked against `html.unescape` ([fixture](../crates/quran-detect/tests/fixtures/unicode-15.1.tsv), generated by [`generate-tables.py`](../scripts/generate-tables.py)).
- The embedded Tanzil files are checked against their pinned SHA-256 hashes, and both scripts against one matching index.
- The reference test suite's behavioral contracts are ported: prefixes, error budgets, each error kind alone, exact-context guards on synthetic corpora, alternatives and explicit choices, reference choices, all formatting combinations, conflicts, scripts, plans and undo.
- The command line is tested for exact bytes (CRLF, emoji, BOM), stdin, overwrite protection, plan files, explicit matches, validation exit codes, completions and argument files.

## Parity with the reference

[`scripts/parity.py`](../scripts/parity.py) runs the reference matcher with a corpus folder holding the same Tanzil text and the same stopword list, and this crate through [`examples/parity.rs`](../crates/quran-detect/examples/parity.rs). For each case it compares, after converting the reference's code-point offsets to UTF-8 byte offsets:

- `identify` and `alternatives`: every field of every match, including edits, scores, ties, reference alternatives and identities;
- plans and outputs for five formatting combinations, and that each plan reverts exactly;
- explicit selections: matches with a `reference_choice`, an unknown choice, compatible non-recommended alternatives, unordered matches and an empty selection.

Cases: every input of the IslamicEval development set, the OCR panel, the Faqieh 10-hour windows and whole transcripts, the Faqieh fresh sample, and the walkthrough confirmation windows and whole transcripts, plus edge cases for markup, entities, ligatures, presentation forms, line endings, decomposed hamza, unassigned characters, citations and brackets. Each text runs with the three presets in both scripts, and texts other than whole transcripts also with six variant configurations: exact context 0 and `1,2`, typo only, structural errors only, join only, and an error fraction of 1 with two edits, two words and context `0,1`.

Result (2026-11-11): all 17,322 cases on 1,463 texts are identical: 124,467 matches, 398,795 alternatives, 2,813,110 plan edits, 59,969 explicit-selection plans and 75,963 changed outputs. The first full run found 520 differences, all in the `error_fraction` of matches read back from JSON in explicit selections, one or two units in the last place: `serde_json`'s default float parser is not correctly rounded. The workspace now enables its `float_roundtrip` feature, a CLI test reproduces the case, and the rerun found no difference. A debug build, which checks integer overflow, also ran 970 sampled cases including every edge case without a panic or difference.

An independent line-by-line review against the reference, with about 1,700 further generated and hand-written cases, found no matching difference. It found three edge cases outside normal detection, all handled: hand-edited plans with offsets near `usize::MAX` are rejected instead of overflowing in `revert`; an explicit `"reference_choice": null` is rejected instead of ignored, as the reference does; and a decimal entity longer than 4,300 digits, which raises an exception in CPython and so in the reference, decodes to U+FFFD.

## Benchmark gate

The reference repository's benchmark runner gained `--engine rust --binary PATH`, which runs this command-line tool for every document (`identify`, then `plan --matches`) and converts offsets for the unchanged, independent scorers. [`scripts/gate.py`](../scripts/gate.py) compares the summaries with the reference's results on its own corpus, `audited-v1`, which differs from Tanzil 1.1 in six verses. The release gate: on each dataset and preset, no headline rate (detection precision, recall and F1; replacement correctness, repair and damage rates for letters, vocalized and normalized words) more than 0.5 points worse, and a non-negative sum of signed differences.

Result (2026-11-11): 138 rates compared across five datasets and three presets; 112 are identical and none is more than 0.5 points worse. The sum of signed differences is -3.203 points, so the gate's second condition fails: **the agreed gate does not pass**. Every changed rate is below:

All seven differing document results trace to two verses that Tanzil corrected in version 1.1, after the reference's corpus was made: 17:32 (`الزِّنا` became `الزِّنىٰ`) in six results and 8:6 (`بَعْدَمَا` became `بَعْدَ مَا`) in one. A damaged quotation written with the old spelling now needs one more edit, so some short fragments no longer fit the budget; and where the restored 17:32 is scored against a reference written with the old spelling, the new spelling counts as damage. The OCR and Faqieh fresh results are identical. Combined with the parity result above, the differences come from the corpus, not from the port. Each "repaired" and "correct" pair counts the same event twice. The maintainer accepted this result for 0.1 on 2026-11-11, because the differences are Tanzil's own corrections.

Datasets have different reference policies: the OCR inventory supports known-fragment recall only, and the Faqieh references are provisional text audits. All of them were used during the reference's development, so they show parity, not generalization. Faqieh v1 is superseded by v2, which uses the same inputs with corrected references.

## Speed

[`scripts/timing.py`](../scripts/timing.py) times identify, plan and apply per document in one long-lived process for each engine, pinned to the same core of an otherwise idle 6-core Linux machine, after loading each corpus once (2026-11-11, wall clock):

|---|---|---:|---:|---:|---:|---:|---:|
| islamiceval | strict | 484 | 3.58 | 0.26 | 5.0 | 0.38 | 13.7× |
| ocr | strict | 500 | 4.13 | 0.39 | 6.5 | 0.55 | 10.6× |
| faqieh-windows | strict | 166 | 2.31 | 0.21 | 10.4 | 0.89 | 11.0× |
| islamiceval | balanced | 484 | 100.81 | 2.41 | 143.4 | 3.46 | 41.9× |
| ocr | balanced | 500 | 155.03 | 3.44 | 267.8 | 5.93 | 45.1× |
| faqieh-windows | balanced | 166 | 104.27 | 2.51 | 587.8 | 14.17 | 41.5× |
| islamiceval | tolerant | 484 | 162.44 | 3.70 | 228.7 | 5.37 | 43.9× |
| ocr | tolerant | 500 | 235.22 | 5.36 | 406.6 | 9.37 | 43.9× |
| faqieh-windows | tolerant | 166 | 176.15 | 3.95 | 987.8 | 22.48 | 44.5× |

The command line additionally builds the corpus index at start-up, about 0.2 seconds per invocation; a long-lived library process pays it once. Speed is reported, not gated.
